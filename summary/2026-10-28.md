    *   크롬 개발자 도구(`F12 -> Network -> Timing`)에서 실시간 막대그래프로 `jwt`(서명 검증), `db-blacklist`(블랙리스트 조회), `db-device`(단말 신뢰 조회), `db-user`(계정/권한 동기화), `ztna-pep`(PEP 총합), `target-upstream`(타겟 프록시 왕복) 시간을 즉시 확인할 수 있도록 구성.
*   **통합 벤치마크 스크립트 구현 (`ztna-gateway/benchmark-overhead.js`) 및 로그 오염 방지 (`accessLogger.js`):**
    *   단일 명령어로 1~4번 오버헤드 실험을 자동 수행하고 통계 표(`Avg`, `p50`, `p95`, `p99`, `Req/sec`)를 출력하는 `benchmark-overhead.js` 작성.

## 4. EC2 실서버 오버헤드 벤치마크 측정 결과 및 분석 문서화 (`docs/OVERHEAD_BENCHMARK_REPORT.md`)
*   **[1번 실험] A/B 경로 응답 지연시간 비교 (각 100회):**
    *   경량 API(`GET /`): Direct `0.87 ms` -> ZTNA Gateway `5.68 ms` (**오버헤드 `+4.80 ms`**)
    *   사내 공지 조회(`GET /api/notices`): Direct `2.44 ms` -> ZTNA Gateway `6.75 ms` (**오버헤드 `+4.31 ms`**)
    *   매 요청마다 4단계 실시간 보안 검증을 수행함에도 추가 지연이 5ms 미만으로 사용자 체감 지연이 전혀 없음을 입증.
*   **[2번 실험] 동시 접속(`Concurrency = 1, 10, 50`) 부하 테스트:**
    *   단일 소형 EC2 인스턴스에서 요청당 3회 실시간 DB 검증을 수행하면서 초당 최대 **`266.2 Req/sec`**(분당 약 16,000건)를 에러 없이 처리(`c = 50` 평균 응답 `174.10 ms`).
*   **[3번 실험 & 추가 분석] 구간별 마이크로 타이밍 및 DB 쿼리 통합 시뮬레이션:**
    *   순수 PEP 검증 시간(`2.656 ms`) 중 JWT 검증이 `37.9%`(`1.006 ms`), DB 3회 순차 조회(`blacklist`, `devices`, `users`)가 **`61.8%`(`1.643 ms`)**를 차지하여 주요 병목임을 규명.
    *   현재의 순차 쿼리 3회(`1.386 ms`)를 단일 `LEFT JOIN` 쿼리 1회(`0.572 ms`)로 통합할 경우 **DB 오버헤드가 `58.7%` 감소(`p95` 기준 `67.2%` 감소)**함을 실측으로 확인(추후 최적화 반영 예정).
*   **[4번 실험] Policy Server 지속적 신뢰 검증(`POST /api/verify-context` Heartbeat) 효율성 검증:**
    *   조건부 토큰 재발급 최적화를 통해 일반 주기 응답 시간이 `4.35 ms -> 3.34 ms`로 평균 **`23.2%` 단축**(`p95` 기준 `37.4%` 단축)되었으며, 1인당 분당 네트워크 대역폭 소모량은 **`0.49 KB/min`**에 불과함을 확인.
*   **보고서 문서화 완료:**
    *   실행 방법, 지표 해석법, 1~4번 실험 시나리오 및 결과 분석을 종합하여 `docs/OVERHEAD_BENCHMARK_REPORT.md`에 저장 완료(10~11주차 생체인증 고도화, `LEFT JOIN` 단일 쿼리 최적화, 11대 모의 해킹 자동 검증 계획은 `docs/WEEK_10_11_PLAN.md`에 별도 보관).

## 5. 모바일/다중 기기 접속 시 위험도 오탐(90점 차단) 및 차단 상태 동기화 버그 해결 (`index.tsx`, `authController.js`)
*   **클라이언트 백그라운드 복귀 및 로그인 직전 IP·GPS 실시간 갱신 (`ztna-client/app/index.tsx`):**
    *   **원인 규명:** `useEffect(..., [])`가 앱 최초 실행 시에만 1회 동작하여, 학교에서 앱을 켰다가(로그인 없이) 집으로 이동해 다시 앱을 열었을 때 메모리에 남아 있던 이전 학교 IP 주소와 학교 GPS 좌표가 갱신되지 않고 그대로 서버에 전송되는 문제 확인.
    *   **조치 내용:** `refreshNetworkAndLocation()` 함수를 분리하여 ① 앱 최초 실행 시, ② 백그라운드에서 포그라운드 복귀 시(`AppState: active`), ③ 로그아웃 후 로그인 화면 복귀 시, ④ 로그인 버튼 클릭 직전에 항상 최신 공인 IP(`cache: 'no-store'`)와 GPS 위치를 새로 수집하도록 수정.
*   **이동 속도(Impossible Travel) 계산 시 단말기별(`device_id`) 시간 기준 분리 (`ztna-policy-server/controllers/authController.js`):**
    *   **원인 규명:** `lastLogin` 조회 시 `device_id` 구분 없이 `user_id` 전체의 마지막 로그를 조회하여, 집 PC 웹 로그인(`16:56:05`) 직후 62초 뒤 스마트폰 앱(`16:57:07`)으로 로그인했을 때 스마트폰의 이동 거리(`22.5km`)를 PC 로그인 후 경과 시간(`62초`)으로 나누어 시속 `1,306km/h`(`+70점`)로 오탐하던 버그 확인.
    *   **조치 내용:** `WHERE user_id = ? AND device_id = ? AND action_taken = 'ALLOW'`로 쿼리를 수정하여 반드시 해당 단말기의 직전 정상 접속 시각과 위치를 짝지어 이동 속도를 계산하도록 개선.
*   **위험도 점수(`70점 이상`) 차단 시 단말 자산 상태(`BLOCKED`) 즉시 반영 (`ztna-policy-server/controllers/authController.js`):**
    *   **원인 규명:** `forceDeny || riskScore >= 70`으로 차단(`DENY`)될 때 `access_logs`에만 기록하고 `devices` 테이블의 `status`를 변경하지 않아, 관리자 대시보드 단말 자산 탭에서 여전히 `인가됨(APPROVED)`으로 표시되던 불일치 확인.
    *   **조치 내용:** 고위험 차단 발생 시 `UPDATE devices SET status = 'BLOCKED', is_trusted = 0 WHERE id = ?`를 즉시 수행하여 관리자 대시보드 단말 자산 탭에서도 즉시 `차단됨(BLOCKED)` 상태로 동기화되도록 수정 및 EC2 반영 완료.
