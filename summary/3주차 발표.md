# 🎤 ZTNA 프로젝트 3주차 발표 대본 및 작업 요약

## 1. 📌 어떤 내용인지 (Overview)
3주차의 핵심 테마는 **"사용자 경험(UX) 극대화"**와 **"엔터프라이즈 모바일 보안(App Security) 강화"**였습니다. 
초기 단계의 단일 화면 구조에서 벗어나 모던한 **3단 하단 탭(Bottom Tabs) UI**를 구축하고, 게시판 및 캘린더 데이터를 실제 MySQL 데이터베이스(DB)와 완벽하게 실시간 연동했습니다.
더불어 ZTNA의 핵심 개념인 '지속적 검증'과 '기밀 유지'를 달성하기 위해, **화면 캡처 원천 방지 기술**과 **생체 인증(FaceID/지문)**을 도입하여 모바일 앱 환경에서의 보안 완성도를 비약적으로 끌어올렸습니다.

---

## 2. 🛠️ 어떤 작업이었는지 (Key Tasks)
- **3단 탭(Bottom Tabs) 네비게이션 개편:** 근태 관리, 기밀 문서 및 게시판, 환경 설정 3개의 탭으로 앱 구조를 완전히 나누어 가독성을 높였습니다.
- **기밀 게시판 및 캘린더 일정 실시간 DB 연동:** 단순 메모리 배열(Mock Data) 기반이었던 게시판과 캘린더를 백엔드 서버(`target.js`) 및 MySQL(`notices`, `events` 테이블)과 영구적으로 연동시켰습니다.
- **모바일 앱 보안 제어 기능 추가:** 인트라넷(사내망) 진입 시 화면 캡처 및 화면 녹화를 막는 기능을 추가하고, 복잡한 이메일 OTP를 대체할 FaceID/지문 인증 수단을 적용했습니다.
- **전역 테마 및 Mobbin 디자인 적용:** 라이트/다크 모드 시스템을 구축하고 `AsyncStorage`를 통해 영구 저장시켰으며, 기존 텍스트 아이콘들을 깔끔한 SVG 아이콘 기반의 라디오 버튼 폼으로 부드럽게 개선했습니다.

## 3. 💻 어떤 코드 수정이었는지 (Code Modifications)

### ① 권한 기반 데이터 제어(RBAC) 로직 완벽 교정
- `target.js`의 게시판/일정 `DELETE`, `PUT` API에 권한 검증 코드를 철저히 적용했습니다.
- **(매우 중요한 픽스)** 기존 로직(`rows[0].author !== '관리자'`)이 '글의 작성자가 관리자인지'를 묻는 치명적인 논리 오류를 띠고 있음을 발견했습니다. 이를 **`currentUser !== '관리자'`(현재 작업을 요청하는 로그인한 당사자가 관리자인가?)** 로 백엔드와 프론트엔드 전 영역에서 싹 통일하여 수정했습니다.

### ② 데이터베이스 스키마 정규화 및 마이그레이션
- 글을 수정할 때 날짜 뒤에 무식하게 `(수정됨)` 이라는 문자열 텍스트를 덧붙이던 임시 로직을 과감히 폐기했습니다.
- DB에 **`is_edited (TINYINT)`**라는 Boolean형 전용 컬럼을 새롭게 파서(`ALTER TABLE`), 프론트엔드에서는 오직 이 Boolean 값만 확인하여 조건부 렌더링을 하도록 코드를 분리했습니다.
- 이 과정에서 발생할 수 있는 중복 컬럼 오류(`ER_DUP_FIELDNAME`)에 대해 예외 처리(try-catch)를 추가하여 서버 구동의 안정성도 확보했습니다.

### ③ 생체 인증(`verify-bio`) 백엔드 로직 신규 분리
- 정책 서버(`auth.js`)의 기존 OTP 검증 라우터 바로 밑에 **`/api/verify-bio`** API를 새로 뚫었습니다. 
- 클라이언트가 `expo-local-authentication` 훅을 통해 로컬 생체 인증(FaceID)을 무사히 통과하고 호출하면, 별도의 6자리 코드 검증 없이 즉시 JWT 출입증을 발급하도록 코드를 수정했습니다.

### ④ 캡처 원천 차단 모듈 연동
- 가장 기밀도가 높은 `IntranetScreen.tsx` 최상단에 `usePreventScreenCapture()` 훅을 선언했습니다. 
- 훅 단 한 줄의 코드로 컴포넌트가 화면에 마운트(렌더링)되는 즉시 OS 레벨의 캡처 및 녹화 기능을 원천 블락하도록 구현했습니다.

## 4. 💡 왜 그렇게 했는지 (Why)

- **`currentUser` 기준으로 권한 로직을 통일한 이유:** 
  기존 방식은 보안팀 계정으로 쓴 글을 일반 사원 누구나 지울 수 있거나, 반대로 관리자가 타인의 글을 통제하지 못하는 **심각한 인가(Authorization) 보안 취약점**이 있었습니다. 권한 확인의 주체는 무조건 '요청을 보낸 당사자'가 되어야 하므로 튼튼한 RBAC 아키텍처를 위해 기준을 명확히 통일했습니다.
- **DB 정규화(`is_edited`)를 진행한 이유:** 
  날짜 필드에 문자열을 합성하면 나중에 시간 순서대로 정렬(`ORDER BY`)을 하거나 프론트에서 시간 포맷터를 사용할 때 무조건 크래시(Crash)가 납니다. 백엔드의 완벽한 **데이터 무결성**을 유지하기 위해 상태값(Boolean)과 데이터값(Date)을 철저하게 분리했습니다.
- **생체 인증(Biometrics)을 도입한 이유:** 
  ZTNA 특성상 네트워크 환경이 바뀌거나 배터리가 줄면 수시로 2차 인증(Step-Up)을 요구하게 됩니다. 이때마다 메일함을 열고 6자리 OTP를 외워서 입력하는 것은 모바일 사용성을 심각하게 해칩니다. 따라서 **'최고 수준의 보안성'과 '사용 편의성'이라는 두 마리 토끼**를 모두 잡기 위해 생체 인증 로직을 추가했습니다.
- **화면 캡처 방지 기능을 고집한 이유:** 
  네트워크 단에서 아무리 훌륭한 게이트웨이 암호화와 ZTNA 검증을 거치더라도, 핸드폰에 뜬 기밀 문서를 스크린샷으로 찍어 외부로 유출하면 모든 방어가 무용지물이 됩니다. 따라서 정보 유출의 가장 취약한 엔드포인트(기기 화면) 자체를 틀어막기 위해 OS 레벨 차단을 결단했습니다.
