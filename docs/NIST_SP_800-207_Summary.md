# NIST SP 800-207 기반 제로 트러스트 아키텍처 (ZTA) 가이드

NIST(미국 국립표준기술연구원)에서 2020년 8월 발표한 **NIST SP 800-207**은 전 세계 제로 트러스트 보안의 사실상 표준(De facto standard) 가이드라인입니다. 기존의 경계선 기반(내부망 신뢰) 모델을 폐기하고, **"결코 신뢰하지 말고, 항상 검증하라(Never Trust, Always Verify)"**는 원칙을 시스템 아키텍처로 정립했습니다.

---

## 1. 제로 트러스트 7대 기본 원칙 (Tenets of Zero Trust)

1. **모든 데이터 원천과 컴퓨팅 서비스는 자원(Resource)으로 간주한다.**
   - 엔드포인트 기기, SaaS, 내부 데이터베이스, 클라우드 리소스 모두가 보호 대상입니다.
2. **네트워크 위치에 관계없이 모든 통신을 보호한다.**
   - 사내 Wi-Fi나 LAN에 접속되어 있어도 신뢰하지 않으며, 모든 통신은 암호화(TLS/mTLS) 및 검증을 거칩니다.
3. **개별 리소스 단위로 세션별 접근 권한을 부여한다.**
   - 한 번 통과했다고 전체 망을 탐색할 수 없으며, 최소 권한 원칙(Least Privilege)에 따라 세션 단위로 인가됩니다.
4. **접근 허용은 동적 정책(Dynamic Policy)에 의해 결정된다.**
   - ID/PW뿐만 아니라 기기 무결성, 보안 패치 상태, 접속 위치, 시간대, 행동 패턴 등 다양한 속성을 동적으로 평가합니다.
5. **모든 자산의 무결성과 보안 상태를 지속적으로 모니터링한다.**
   - 세션 체결 이후에도 루팅, 탈옥, 악성코드 감염 여부를 실시간(Heartbeat)으로 지속 평가합니다.
6. **모든 리소스 인증과 인가는 동적이며 접근 전에 엄격히 수행된다.**
   - 위험 기반의 추가 인증(MFA, Step-up Auth, OTP)을 적용합니다.
7. **가능한 많은 상태 정보를 수집하여 향후 정책 개선에 반영한다.**
   - 접속 로그, 네트워크 트래픽, 보안 위협 데이터를 수집하여 모니터링 및 감사에 활용합니다.

## 2. 논리적 핵심 아키텍처 (PDP / PEP 모델)

NIST SP 800-207은 보안 제어를 **제어 영역(Control Plane)**과 **데이터 영역(Data Plane)**으로 명확히 분리합니다.

```
+-------------------------------------------------------------+
|               Control Plane (제어 영역)                     |
|                                                             |
|   +---------------------+        +----------------------+   |
|   | Policy Engine (PE)  | <----> | Policy Admin (PA)    |   |
|   | (정책 판단/결정의 뇌)  |        | (토큰 발급/세션 관리) |   |
|   +---------------------+        +----------------------+   |
|              \                     /                        |
|               \                   /                         |
|             PDP (Policy Decision Point)                     |
+-------------------------------------------------------------+
                              |
               인증 통과 시 출입증(JWT) 발급
                              |
                              v
+-------------------------------------------------------------+
|                Data Plane (데이터 영역)                      |
|                                                             |
|   [사용자 / 클라이언트]                                       |
|             |                                               |
|             v (토큰 및 요청 전송)                             |
|   +------------------------------------+                    |
|   | Policy Enforcement Point (PEP)     |                    |
|   | (문지기 / 게이트웨이 프록시)       |                    |
|   +------------------------------------+                    |
|             |                                               |
|             v (인가된 트래픽만 전달)                         |
|   [사내 자원 / 대상 시스템 (ERP, DB)]                        |
+-------------------------------------------------------------+
```

### 핵심 컴포넌트 역할
1. **PDP (Policy Decision Point, 정책 결정 지점)**
   - **PE (Policy Engine)**: 사용자 신원, 역할, 기기 무결성, 네트워크 컨텍스트를 종합 평가하여 접근 허용/차단 여부를 최종 결정합니다.
   - **PA (Policy Administrator)**: PE의 결정에 따라 세션을 시작/종료하고 접근 토큰(출입증)을 발급/폐기합니다.
   - *우리 시스템 대응*: `ztna-policy-server`
2. **PEP (Policy Enforcement Point, 정책 실행 지점)**
   - 클라이언트와 실제 자원 사이에서 트래픽을 가로채 검사하는 문지기입니다.
   - 유효한 토큰이 없거나 부여된 권한 범위를 벗어난 요청을 물리적/논리적으로 원천 차단합니다.
   - *우리 시스템 대응*: `ztna-gateway`

## 3. 접근 제어 모델: RBAC vs ABAC

| 구분 | RBAC (역할 기반 제어) | ABAC (속성 기반 제어) |
| :--- | :--- | :--- |
| **판단 기준** | 사용자의 직책/역할 (`Role`) | **주체, 객체, 행동, 환경의 다양한 속성 조합** |
| **장점** | 구조가 단순하고 권한 관리가 직관적임 | 매우 유연하며 동적인 상황 변화 반영 가능 |
| **단점** | 역할 폭발(Role Explosion) 한계 발생 | 정책 규칙 설계가 정교해야 함 |
| **ZTNA 활용** | 1차적 접근 기준 (부서, 직급) | **상황별 동적 통제 (기기 상태, 위치, 네트워크)** |

> **하이브리드 모델**: 본 프로젝트에서는 기본적인 부서 권한(RBAC) 위에 기기 및 접속 환경 속성(ABAC)을 결합한 정책 엔진을 사용합니다.

---

## 4. 본 프로젝트 구현 적용 시나리오

PDP 정책 엔진은 **[사용자 역할(RBAC) + 기기 소유/보안 상태 + 네트워크/위치(ABAC)]**를 조합하여 3단계 결정을 내립니다.

### 1) 완전 허용 (Allow)
- **조건**: `등록 및 승인된 법인 기기(CORPORATE, status = APPROVED, is_compliant = 1)` AND `총 위험도 점수 < 30점`
- **동작**: 2차 인증 생략 후 즉시 로그인, 사내망 전체 기능(근태, 기밀문서, 공지사항, 일정) 접근 및 기밀문서 다운로드·업로드(과장 이상) 허용

### 2) 조건부 허용 (Step-up Auth / 제한적 허용)
- **조건**: `개인 단말(BYOD)` OR `30점 <= 총 위험도 점수 < 70점` (신규 기기, 새로운 IP 대역, 장거리 이동, 업무 시간 외 접속 등)
- **동작**:
  - 2차 인증(6자리 이메일 OTP 또는 기기 전용 암호화 비밀키 `bioToken`이 결합된 생체 인증) 필수 통과 요구
  - 신규 미등록 기기는 OTP 통과 시 `PENDING` 상태 및 `bio_token_hash`가 등록되며 관리자 승인 후 접속 가능
  - `BYOD` 기기는 출입증(JWT) 및 실시간 게이트웨이 동기화 헤더에 `allowDownload: false`가 부여되어 **기밀문서 다운로드·업로드가 원천 차단**되고 사내 일정(`Schedule`) 탭이 숨겨지며, 모바일 앱에서는 사내망 진입 중 OS 화면 캡처(`expo-screen-capture`)가 차단됩니다.

### 3) 즉시 차단 (Deny)
- **조건**: `모바일 루팅/탈옥 감지` OR `관리자 차단 기기(status = BLOCKED)` OR `컴플라이언스 위반(is_compliant = 0)` OR `총 위험도 점수 >= 70점` (Impossible Travel 등)
- **동작**: 토큰 발급 원천 거부, 해당 기기 상태 즉시 `BLOCKED` 전환 및 생체 인증 비밀키(`bio_token_hash`) 폐기, 접속 차단 화면(`BlockedScreen`) 전환 및 관리자 대시보드 실시간 고위험 알림 발생
- **구현 현황**: 클라이언트는 모바일 환경에서 `utils/deviceSecurity.ts`의 `Device.isRootedExperimentalAsync()`를 통해 로그인 직전 및 30초 주기의 Heartbeat마다 루팅/탈옥 여부를 실시간 점검하며, 감지 시 즉시 앱 사용을 차단하고 세션을 강제 종료합니다. 서버(`authController.js`) 또한 `isRooted`, `status !== 'APPROVED'`, `is_compliant === 0`, `riskScore >= 70` 조건을 평가하여 즉시 차단합니다.
