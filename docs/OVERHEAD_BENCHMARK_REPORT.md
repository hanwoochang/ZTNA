# ZTNA 아키텍처 보안 오버헤드(Overhead) 벤치마크 가이드 및 결과 분석 보고서

- **작성일:** 2026-10-28
- **측정 환경:** AWS EC2 (`ubuntu@54.79.43.69`, Node.js v22, MySQL 8.0, PM2 프로세스 관리)
- **관련 소스 파일:**
  - 벤치마크 스크립트: `ztna-gateway/benchmark-overhead.js`
  - 게이트웨이 PEP 타이밍 측정: `ztna-gateway/server.js`, `ztna-gateway/middlewares/accessLogger.js`
  - 정책 서버 PDP 타이밍 측정: `ztna-policy-server/server.js`, `ztna-policy-server/controllers/authController.js`

## 1. 테스트 개요 및 목적

Zero Trust Network Access (ZTNA) 아키텍처는 기존의 경계 기반 보안(한 번 로그인하면 내부망 전체를 신뢰하는 방식)과 달리, **"결코 신뢰하지 말고 항상 검증하라(Never Trust, Always Verify)"** 원칙에 따라 **매 API 요청마다 실시간 인증·인가·단말 신뢰성 검증**을 수행합니다.

본 문서는 이러한 실시간 보안 검증 계층(PEP/PDP)이 시스템 응답 속도(Latency), 동시 처리량(Throughput), 네트워크 대역폭에 미치는 **보안 오버헤드(Security Overhead)**를 정량적으로 측정하는 실행 방법과 실측 데이터 분석 결과를 정리한 문서입니다.

## 2. 오버헤드 테스트 직접 실행 및 확인 방법

오버헤드 측정은 **1) 터미널 통합 벤치마크 스크립트 실행**과 **2) 브라우저 개발자 도구(`F12`) 실시간 확인** 두 가지 방법으로 언제든 직접 수행할 수 있습니다.

### 방법 1: 터미널에서 통합 벤치마크 스크립트(`benchmark-overhead.js`) 실행

로컬 Windows PowerShell에서 아래 명령어를 실행하면 EC2 서버에 접속하여 1~4번 실험을 자동으로 수행하고 결과 표를 출력합니다.

```powershell
ssh -i C:\Users\043kw\Downloads\ztna-key.pem ubuntu@54.79.43.69 "cd /home/ubuntu/ztna/ztna-gateway && node benchmark-overhead.js"
```

*(이미 EC2 서버에 SSH로 접속해 있는 상태라면 아래 명령어만 입력하면 됩니다.)*

```bash
cd /home/ubuntu/ztna/ztna-gateway && node benchmark-overhead.js
```

#### 벤치마크 스크립트의 자동 처리 사항
1. **테스트 계정 및 기기 자동 조회:** DB에서 활성화된 계정(`is_active = 1`)과 승인된 단말(`status = 'APPROVED'`)을 자동으로 1건 조회하여 메모리상에서 임시 테스트용 JWT를 생성합니다.
2. **DB 감사 로그 오염 방지:** 모든 벤치마크 요청에는 `x-ztna-benchmark: true` 헤더가 포함되며, `ztna-gateway/middlewares/accessLogger.js`에서 해당 헤더가 있는 요청은 `intranet_access_logs` 테이블에 기록하지 않도록 예외 처리되어 있습니다.
3. **커넥션 웜업(Warm-up):** 초기 TCP 연결 수립 비용이 통계에 섞이지 않도록 본 실험 전 10회의 사전 호출(Warm-up)을 먼저 수행합니다.

### 방법 2: 크롬 브라우저 개발자 도구(`F12`)에서 `Server-Timing` 막대그래프 확인

`ztna-gateway/server.js` 및 `ztna-policy-server/controllers/authController.js`에 W3C 표준 HTTP `Server-Timing` 응답 헤더가 적용되어 있어, 실제 웹 앱을 조작하면서 실시간으로 오버헤드를 확인할 수 있습니다.

1. 크롬 브라우저에서 클라이언트 웹(`https://ztna-core.duckdns.org/app/`)에 접속하여 로그인합니다.
2. 키보드 `F12`를 눌러 개발자 도구를 열고 **Network(네트워크)** 탭으로 이동합니다.
3. 앱 내 탭을 클릭하거나 새로고침하여 발생하는 API 요청(`notices`, `documents`, `today`, `verify-context` 등) 중 하나를 클릭합니다.
4. 우측 상세 패널에서 **Timing(타이밍)** 탭을 클릭하고 맨 아래 **Server Timing** 섹션을 확인합니다.
5. 아래와 같이 각 보안 검증 단계별 소요 시간이 시각적인 막대그래프와 수치(`ms`)로 표시됩니다:
   - `JWT Verify` (`jwt`): JWT 암호화 서명 검증 소요 시간
   - `DB Blacklist Check` (`db-blacklist`): 폐기된 토큰 여부 DB 조회 시간
   - `DB Device Trust` (`db-device`): 단말기 승인 상태(`APPROVED`) 및 `BYOD`/`CORPORATE` 조회 시간
   - `DB User Sync` (`db-user`): 계정 활성 상태(`is_active`) 및 직급/부서 실시간 동기화 시간
   - `ZTNA PEP Total` (`ztna-pep`): ZTNA 게이트웨이 보안 검증 총 소요 시간
   - `Target Server` (`target-upstream`): 내부 보호 대상 서버(`5000번 포트`) 프록시 왕복 시간

## 3. 측정 지표(Metrics) 용어 설명

| 지표명 | 의미 및 해석 방법 |
| :--- | :--- |
| **`Avg (ms)`** | 전체 반복 요청(100회 또는 300회)의 **산술 평균 응답 시간**입니다 (`1 ms = 0.001초`). |
| **`p50 (ms)`** | 전체 응답 시간을 크기순으로 줄 세웠을 때 **정중앙(50% 지점)에 위치하는 중앙값(Median)**으로, 일반 사용자가 가장 흔하게 체감하는 응답 속도입니다. |
| **`p95 (ms)`** | 하위 95% 지점의 응답 시간입니다. 즉, **100번 요청 중 95번은 이 시간 이내에 처리됨**을 보장하는 지표입니다. |
| **`p99 (ms)`** | 하위 99% 지점의 응답 시간으로, 일시적인 지연을 포함한 최악의 상황에 가까운 상위 1% 경계 지표입니다. |
| **`처리량 (Req/sec, RPS)`** | 서버가 **1초 동안 성공적으로 처리해 낸 총 요청 수**입니다. 수치가 높을수록 서버의 동시 처리 능력이 뛰어남을 의미합니다. |
| **`동시 접속 (c)`** | 동시에 쉬지 않고 요청을 보내는 **가상 사용자(Worker)의 수**입니다 (`c = 1, 10, 50`). |

## 4. 실험별 시나리오 설명 및 실측 결과 분석

### [1번 실험] A/B 경로 응답 지연시간 비교 (반복 횟수: 각 100회)

#### 1) 테스트한 상황
동일한 API를 **보안 검사가 없는 직접 호출 경로(Direct - Baseline)**와 **ZTNA 게이트웨이를 통과하는 경로(With ZTNA)**로 각각 100회씩 호출하여 순수 ZTNA 보안 오버헤드를 산출한 실험입니다.
- **Direct (`5000번 포트` 직접 호출):** 기존 경계형 사내망처럼 내부 웹 서버(`ztna-gateway/target.js`)에 아무런 추가 검증 없이 바로 접근하는 상황입니다.
- **ZTNA Gateway (`4000번 포트` 경유 호출):** 게이트웨이(`ztna-gateway/server.js`)의 `verifyToken` 미들웨어가 ① JWT 서명 검증 -> ② `token_blacklist` DB 조회 -> ③ `devices` 승인 및 소유 형태(`BYOD`/`CORPORATE`) DB 조회 -> ④ `users` 활성 상태 및 직급/부서 DB 조회 -> ⑤ HTTP 리버스 프록시 헤더 주입 및 전달까지 전 과정을 수행하는 상황입니다.
- 이를 **단순 응답 API(`GET /`)**와 **실제 DB에서 공지사항 목록을 조회하는 업무 API(`GET /api/notices`)** 두 가지 케이스로 나누어 측정했습니다.

#### 2) 실측 결과
| index | 비교 구간 | Avg (ms) | p50 (ms) | p95 (ms) | p99 (ms) | ZTNA 오버헤드 |
| :---: | :--- | :---: | :---: | :---: | :---: | :---: |
| 0 | 경량 API (`GET /`) - Direct (No ZTNA) | `0.87` | `0.77` | `1.58` | `2.76` | Baseline |
| 1 | 경량 API (`GET /private/`) - ZTNA Gateway | `5.68` | `4.80` | `10.45` | `19.02` | **`+4.80 ms`** |
| 2 | 사내 공지 조회 (`GET /api/notices`) - Direct | `2.44` | `2.16` | `4.11` | `5.16` | Baseline |
| 3 | 사내 공지 조회 (`GET /private/api/notices`) - ZTNA | `6.75` | `6.17` | `9.90` | `11.35` | **`+4.31 ms`** |

#### 3) 결과 분석
- ZTNA 게이트웨이를 경유할 때 추가되는 보안 오버헤드는 경량 API에서 **`+4.80 ms`**, 실제 업무 API(공지 조회)에서 **`+4.31 ms`**로 측정되었습니다.
- 인간이 웹/앱 조작 시 지연을 인지하는 최소 임계값은 약 `100 ms`(0.1초)입니다. **`4.31 ~ 4.80 ms`(약 0.0045초)의 오버헤드는 사용자가 체감하는 속도 저하가 전혀 없음을 의미**하며, 사용성을 해치지 않으면서 매 요청 단위의 실시간 Zero Trust 검증을 달성했음을 입증합니다.

### [2번 실험] 동시 접속(Concurrency) 부하 테스트 — 처리량(RPS) 및 지연시간 비교

#### 1) 테스트한 상황
사내 직원 **1명(`c = 1`), 10명(`c = 10`), 50명(`c = 50`)이 동시에 사내망에 접속해 지연 없이 연속으로 API 요청(총 100~300회)을 쏟아내는 고부하(Peak Traffic) 상황**을 시뮬레이션한 실험입니다.

#### 2) 실측 결과
| index | 동시 접속(c) | 경로 | 처리량 (Req/sec) | Avg (ms) | p95 (ms) | p99 (ms) |
| :---: | :---: | :--- | :---: | :---: | :---: | :---: |
| 0 | `c = 1` | Direct (타겟 직접) | `1324.5` | `0.70` | `0.85` | `5.19` |
| 1 | `c = 1` | ZTNA Gateway 경유 | `200.5` | `4.90` | `7.57` | `10.55` |
| 2 | `c = 10` | Direct (타겟 직접) | `1662.2` | `5.86` | `14.02` | `16.87` |
| 3 | `c = 10` | ZTNA Gateway 경유 | `252.0` | `39.38` | `55.69` | `64.03` |
| 4 | `c = 50` | Direct (타겟 직접) | `1744.3` | `26.59` | `42.82` | `51.94` |
| 5 | `c = 50` | ZTNA Gateway 경유 | **`266.2`** | `174.10` | `213.03` | `239.97` |

#### 3) 결과 분석
- **처리량 차이의 원인:** Direct 경로(`1,744.3 Req/sec`)는 DB 조회 없이 메모리에서 즉시 JSON을 반환하는 반면, ZTNA Gateway 경로(`266.2 Req/sec`)는 **요청 1건당 3번의 실시간 MySQL 쿼리(초당 약 800회의 DB 쿼리)**와 암호화 서명 검증, 프록시 스트림 중계를 수행하기 때문입니다.
- **시스템 안정성 검증:** 단일 소형 EC2 인스턴스에서도 매 요청마다 3단계 DB 검증을 수행하며 **초당 최대 `266.2건`(분당 약 15,970건)**의 사내망 요청을 단 1건의 실패 없이 처리했습니다. 동시 접속자 50명이 쉴 새 없이 요청을 보내는 극한 부하에서도 평균 **`174.10 ms`(약 0.17초)** 내에 안정적으로 응답합니다.

### [3번 실험] ZTNA Gateway (PEP) 내부 구간별 마이크로 타이밍 (`Server-Timing` 헤더 분석)

#### 1) 테스트한 상황
1번 실험에서 확인된 약 `4.3 ~ 4.8 ms`의 ZTNA 오버헤드가 **게이트웨이 내부의 어느 보안 단계에서 얼마나 소비되는지** `process.hrtime.bigint()`(나노초 정밀 타이머)와 `Server-Timing` 헤더를 이용해 5개 세부 구간으로 분해 측정한 실험입니다.

#### 2) 실측 결과
| index | 세부 단계 (`Server-Timing`) | Avg (ms) | p95 (ms) | PEP 내 비중 (%) |
| :---: | :--- | :---: | :---: | :---: |
| 0 | 1. JWT 서명 검증 (`jwt`) | `1.006` | `1.487` | `37.9%` |
| 1 | 2. DB 블랙리스트 조회 (`db-blacklist`) | `0.588` | `1.474` | `22.1%` |
| 2 | 3. DB 기기 신뢰 상태 조회 (`db-device`) | `0.581` | `1.646` | `21.9%` |
| 3 | 4. DB 계정/권한 동기화 (`db-user`) | `0.474` | `1.084` | `17.8%` |
| 4 | **[합계] ZTNA PEP 보안 검증 총합 (`ztna-pep`)** | **`2.656`** | **`4.207`** | **`100.0%`** |
| 5 | 5. 타겟 서버 프록시 왕복 (`target-upstream`) | `1.592` | `3.904` | (전체 대비 `37.5%`) |

#### 3) 결과 분석
- 게이트웨이 내부에서 순수하게 보안 정책을 검증하는 시간(`ztna-pep`)은 평균 **`2.656 ms`**입니다.
- **세부 비중 분석:**
  - **DB 3단계 실시간 조회 합계(`0.588 + 0.581 + 0.474 = 1.643 ms`):** 전체 PEP 검증 시간의 **`61.8%`**를 차지하여 가장 큰 비중을 보였습니다.
  - **JWT 암호화 서명 검증(`1.006 ms`):** CPU 연산이 수반되는 과정으로 전체 PEP 검증 시간의 **`37.9%`**를 차지했습니다.
- 즉, ZTNA 오버헤드의 핵심 병목 지점은 **매 요청마다 순차적으로 3번 발생하는 DB 네트워크 왕복 비용(`61.8%`)**임을 정량적으로 규명했습니다.

### [3-추가 분석] DB 검증 쿼리 구조 비교 (순차 3회 쿼리 vs 단일 `LEFT JOIN` 1회 쿼리)

#### 1) 테스트한 상황
3번 실험을 통해 규명된 DB 왕복 병목(3회 순차 쿼리)을 개선하기 위해, **현재 방식(`token_blacklist` -> `devices` -> `users` 3번 순차 조회)**과 **3개 테이블을 `LEFT JOIN`으로 묶어 DB에 1번만 질의하는 통합 쿼리 방식**을 각 100회 실행하여 성능을 비교한 실험입니다.

#### 2) 실측 결과
| index | DB 조회 방식 | Avg (ms) | p50 (ms) | p95 (ms) | 비고 |
| :---: | :--- | :---: | :---: | :---: | :--- |
| 0 | 현재 방식 (순차 쿼리 3회: `blacklist -> devices -> users`) | `1.386` | `1.202` | `2.461` | DB 네트워크 왕복 3회 |
| 1 | 통합 방식 (단일 `LEFT JOIN` 쿼리 1회) | **`0.572`** | **`0.524`** | **`0.808`** | **DB 오버헤드 `58.7%` 감소 (왕복 1회)** |

#### 3) 결과 분석
- 3개의 개별 쿼리를 단일 `LEFT JOIN` 쿼리 1회로 통합할 경우, 평균 DB 검증 소요 시간이 `1.386 ms`에서 **`0.572 ms`**로 줄어들어 **DB 검증 오버헤드가 `58.7%` 감소**합니다.
- 특히 상위 95% 지연시간(`p95`)은 `2.461 ms`에서 **`0.808 ms`**로 **`67.2%` 단축**되어, 동시 접속자가 몰리는 상황에서 DB 커넥션 풀 점유 시간을 크게 줄일 수 있는 핵심 최적화 방안임을 입증했습니다.

### [4번 실험] Policy Server 지속적 신뢰 검증 (Heartbeat: `POST /api/verify-context`)

#### 1) 테스트한 상황
사용자가 로그인한 이후에도 백그라운드에서 주기적으로 단말 상태(기기 차단 여부, 계정 정지 여부, IP 변경 감지, `BYOD`/`CORPORATE` 권한 변경)를 재검증하는 **지속적 신뢰 검증(Continuous Verification / Heartbeat)** API(`POST /api/verify-context`)의 오버헤드를 측정한 실험입니다.
- **일반 주기 (`0번` 행):** 토큰 만료 시간이 5분 이상 남아 있어, 무거운 신규 JWT 암호화 서명(`jwt.sign`)을 생략하고 기존 토큰을 그대로 유지하는 최적화된 상황입니다.
- **갱신 주기 (`1번` 행):** 토큰 만료가 5분 이하로 임박했거나 권한이 변경되어 신규 JWT를 서명·발급하는 상황입니다.

#### 3) 결과 분석
- **토큰 재발급 최적화 효과:** 매 Heartbeat마다 무조건 새 토큰을 발급할 때(`4.35 ms`)와 비교하여, 만료 5분 전 또는 권한 변경 시에만 재발급하도록 최적화한 일반 주기(`3.34 ms`)에서는 **평균 응답 시간이 `23.2%` 단축**되었으며, **`p95` 지연시간은 `7.88 ms -> 4.93 ms`로 `37.4%` 단축**되었습니다.
- **네트워크 및 모바일 리소스 효율성:** 1회 Heartbeat 왕복 데이터 크기는 약 **`501 Bytes`**로, 1분 주기로 검증할 때 사용자 1인당 네트워크 대역폭 소모량은 **`0.49 KB/min`**(1시간 동안 사용해도 약 `29.4 KB`)에 불과합니다. 모바일(LTE/5G) 환경에서도 데이터 및 배터리 소모 없이 즉각적인 세션 강제 차단(Session Tearing)과 동적 권한 제어(BYOD 다운로드 통제)를 유지할 수 있음을 증명합니다.

## 5. 종합 결론 요약

1. **체감 지연 없는 실시간 보안(`+4.31 ~ 4.80 ms`):** 매 API 요청마다 토큰 폐기 여부, 단말기 승인 여부, 계정 활성 및 권한 동기화를 실시간으로 수행함에도 추가 지연시간은 **5ms 미만**으로 사용자 경험(UX)에 영향을 주지 않습니다.
2. **병목 구간 규명 및 최적화 근거 확보(`58.7%` 절감 가능):** `Server-Timing` 마이크로 타이밍 분석을 통해 전체 PEP 검증 시간(`2.656 ms`) 중 DB 3회 순차 조회가 `61.8%`를 차지함을 밝혔고, 이를 단일 `LEFT JOIN` 쿼리로 통합 시 DB 오버헤드를 **`58.7%`** 줄일 수 있음을 실측으로 확인했습니다.
3. **초경량 지속적 신뢰 검증(`0.49 KB/min`, `3.34 ms`):** 조건부 JWT 재발급 최적화를 통해 Heartbeat 지연을 평균 `23.2%`(`p95` 기준 `37.4%`) 단축했으며, 분당 `0.49 KB`의 초소형 트래픽만으로 실시간 기기 퇴출 및 권한 동기화를 달성했습니다.
